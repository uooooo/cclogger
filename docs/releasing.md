# Cutting a release

Nothing here happens on a merge. A release is a **pushed tag**, and everything else
follows from it.

## What a tag produces

Pushing a tag matching `v<major>.<minor>.<patch>` runs
[`.github/workflows/release.yml`](../.github/workflows/release.yml) — generated by
[`dist`](https://opensource.axo.dev/cargo-dist/) from
[`dist-workspace.toml`](../dist-workspace.toml), not written by hand — which builds on
three runners and creates one GitHub Release holding:

| Asset | What it is |
| --- | --- |
| `cclogger-cli-aarch64-apple-darwin.tar.xz` | the `cclogger` binary, Apple Silicon |
| `cclogger-cli-x86_64-apple-darwin.tar.xz` | the `cclogger` binary, Intel Mac |
| `cclogger-cli-x86_64-unknown-linux-gnu.tar.xz` | the `cclogger` binary, x86\_64 Linux |
| `cclogger-cli-installer.sh` | shell installer that fetches the right one of the above |
| `cclogger-cli-npm-package.tar.gz` | the npm package, **built but not published** |
| `source.tar.gz`, `*.sha256`, `sha256.sum` | source snapshot and checksums |

Each archive also carries `README.md` and `LICENSE`.

**The assets are named `cclogger-cli-*` while the binary inside is `cclogger`.** `dist`
names artifacts after the Cargo package, and the Cargo package is `cclogger-cli`; the npm
package name is overridden to `cclogger` because that one is user-visible. The `-cli`
suffix is the workspace layout showing through — the Cargo packages carried the old
`cclog-` prefix until packaging made them user-visible, which is what got them renamed
([ADR-0003](adr/0003-name.md)).

**Windows is absent on purpose.** `cclogger-archive` uses `std::os::unix` to hold the
archive at 0600 under a 0700 directory — it does not compile for Windows, and the
property it enforces has no equivalent there. Do not add the target to
`dist-workspace.toml`. Someone who runs the npm package on Windows gets an explicit
"not supported by cclogger" error naming the three platforms that are.

## Before you tag

1. **The gate.** [`.github/workflows/ci.yml`](../.github/workflows/ci.yml) runs it on
   every push to `main` and every pull request, so the commit you are about to tag has
   already been through it. Run it locally anyway before you push — it is the same
   commands, and finding out here is faster than finding out from a red run:

   ```bash
   cargo test --workspace --no-fail-fast
   cargo fmt --check
   cargo clippy --workspace --all-targets -- -D warnings
   ```

   plus both conformance commands.

   Note that a **tag** does not re-run any of this: `release.yml` builds and does not
   test. What protects a release is that the commit under the tag was already green on
   `main`. Tagging something that never was — a detached commit, a branch that skipped
   the PR — skips the gate entirely.

   CI pins Rust to the `rust-version` floor in `Cargo.toml` rather than using the
   runner's newest, so a source build that would fail for a user on that version fails
   here first. Your own toolchain is probably newer; the two can disagree, and CI is the
   one that decides.

2. **Set the version.** `version` in `[workspace.package]` of the root `Cargo.toml`, then
   `cargo check` to refresh `Cargo.lock`. The tag must match it: `version = "0.1.2"` →
   tag `v0.1.2`. A mismatch fails the workflow's `plan` job — `dist` refuses and prints
   the tag that would have worked — rather than releasing something mislabelled.

   Pre-1.0, so: minor for a breaking change, patch otherwise. The ledger schema counts
   as an interface here — a change that needs a re-import is a breaking change.

3. **Check the plan.** From a clean tree:

   ```bash
   dist plan
   ```

   It prints the tag it would announce and every artifact it would build. If `dist` is
   not installed, the workflow's `plan` job runs the same command on every pull request,
   so a PR that breaks the config fails there.

4. **On the first release only:** delete the two "not published yet" notes, in the
   README's Install section and in `skills/cclogger/SKILL.md` §0. Both are marked with an
   HTML comment saying so, so `grep -rn 'published yet'` finds them.

## Tagging

```bash
git tag v0.1.0
git push origin v0.1.0
```

Then watch the run. On success there is a GitHub Release with the assets above; on
failure there is no Release and no partial state to clean up beyond the tag.

To redo a tag that failed before the Release was created: `git tag -d v0.1.0 && git push
origin :v0.1.0`, fix, tag again. Once a Release exists, do **not** re-cut the same
version — the npm registry refuses a republished version anyway. Bump the patch.

`dist` writes the release notes itself: install instructions plus a download table. It
picks up a `## [x.y.z]` section from a `CHANGELOG.md` if one exists; there is none here,
so the notes are the install instructions alone.

## Publishing the npm package — a separate, manual step

The workflow builds `cclogger-cli-npm-package.tar.gz` and stops. Nothing in this repository
has ever published to npm, and no `NPM_TOKEN` is configured.

```bash
npm whoami                                    # or `npm login` first
gh release download v0.1.0 --pattern 'cclogger-cli-npm-package.tar.gz'
tar tzf cclogger-cli-npm-package.tar.gz          # look at it before you publish it
npm publish cclogger-cli-npm-package.tar.gz
```

Publish **that** tarball, not a locally rebuilt one. Its `package.json` carries
`name: cclogger`, the release's version, and absolute download URLs pointing at that
release's assets — a local rebuild is only identical if your tree is identical.

**Do this promptly.** The Release's own generated notes tell people to run
`npm install cclogger@<version>`, so between the tag and the publish the release
advertises something that does not exist.

`dist` can do this in CI instead (`publish-jobs = ["npm"]` in `dist-workspace.toml` plus
an `NPM_TOKEN` secret). Deliberately not enabled: it would mean a pushed tag publishes to
a public registry with no human between the two.

## Checking a release actually works

The pipeline is only ever proven by a real release. After the first one:

```bash
curl --proto '=https' --tlsv1.2 -LsSf \
  https://github.com/uooooo/cclogger/releases/latest/download/cclogger-cli-installer.sh | sh
cclogger --version            # expect the version you tagged

npx cclogger@0.1.0 --version  # after `npm publish`; downloads the same binary
```

Test both on macOS and on Linux if you can — the Linux build is the one nothing else
here exercises. The npm route additionally proves the download-at-install-time path,
which is the part that can only fail at a user's machine.

## crates.io: not yet, on purpose

Every crate is `publish = false`, and `[package.metadata.dist] dist = true` on
`cclogger-cli` is what lets `dist` build a binary from it anyway. Do not flip `publish`
to take the name: `cclogger` is free on crates.io, and claiming it pins a public API
while the CLI surface and the ledger schema are both still moving. `dist` does not ask
for it and will not nag.

## Changing the release config

Edit `dist-workspace.toml`, then regenerate rather than hand-editing the workflow:

```bash
dist init --yes        # rewrites .github/workflows/release.yml from the config
```

`dist generate --mode=ci --check` reports whether the committed workflow still matches
the config.

Upgrading `dist` itself means bumping `cargo-dist-version` and regenerating; the version
is pinned there so CI and your machine run the same one.
